Hybrid Search: Cross-Layer Retrieval & Scoring

How Seme combines keyword, semantic, and graph search into one LLM-ready context block

1. The Problem with Single-Layer Search

Traditional memory systems search one layer at a time. A keyword search finds memories containing "TypeScript" but misses the wiki page about TypeScript, the graph entity "TypeScript", and the conversation turn where it was mentioned. The user gets fragmented results and the LLM has to piece them together.

Hybrid search queries all layers simultaneously and returns a unified, LLM-ready context block. One search call returns memories, wiki pages, graph entities, and relevant turns — ranked and formatted for the LLM to consume.

2. Search Layers

Seme's hybrid search operates across four layers:

2.1 Memory Layer (FTS5)

Full-text search over memory value_text, subject, and predicate using SQLite's FTS5 virtual table. FTS5 supports BM25 ranking, prefix matching, and phrase queries. The search sanitizes the query to remove FTS5 special characters (?, *, quotes) that would cause syntax errors.

Fallback: if FTS5 fails (syntax error), the system falls back to exact keyword matching — splitting the query into words and checking if any word appears in the memory text.

2.2 Wiki Layer

LIKE-based search over wiki page titles, content, and entity names. Wiki pages contain compiled knowledge about entities, so searching them surfaces structured information that raw memories don't capture.

2.3 Graph Layer

Entity name matching (LIKE query on entity names and aliases) followed by 2-hop traversal. If the user searches "TypeScript", the system finds the TypeScript entity, then traverses to related entities (React, Node.js, Ponti Studios) and includes them in the results.

2.4 Turn Layer (FTS5)

Full-text search over conversation turns. This surfaces the original conversation context where a topic was discussed, providing provenance and nuance that extracted memories might lose.

3. Scoring and Ranking

Each layer produces results with a score between 0 and 1:

  • FTS5 results: Ranked by BM25 (SQLite's built-in relevance scoring)
  • Keyword fallback: Score = 1 - (position / total), linear decay
  • Wiki results: Score = 1 - (position / total), linear decay
  • Graph results: All matched entities get score 1.0 (binary match)

Results from all layers are combined into a single context block, ordered by layer priority: Memories → Wiki → Graph → Turns. This ordering reflects the information density of each layer — memories are atomic facts, wiki pages are compiled knowledge, graph entities are structural, and turns are raw conversation.

4. Temporal Filtering

The hybrid search supports temporal parameters (since, before, asOf) that filter memories by their observed_at timestamp. This enables "as of" queries: "What did we know about TypeScript before March 2026?"

The temporal filter is applied at the SQL level: WHERE observed_at >= ? AND observed_at <= ?. This is efficient because observed_at is indexed.

5. Abstention Logic

If no results are found across all layers (total_results = 0), the system returns abstain: true. This signals to the LLM that it should not answer from parametric knowledge — the system has no relevant information.

Abstention is critical for preventing hallucination. Without it, the LLM would generate plausible-sounding but potentially incorrect answers for topics the user never discussed.

6. LLM-Ready Context Format

The search result includes a context string formatted as markdown:

## Memories
- [fact] The user uses TypeScript for both frontend and backend.
- [preference] The user prefers dark mode.

## Knowledge Graph
- TypeScript (tool)
- React (tool)

## Relevant Turns
- [Source: TS Facts] TypeScript is a typed superset of JavaScript.

This format is designed for direct injection into an LLM prompt. The LLM can parse the sections and use the information to generate a contextual response.

7. Design Decisions

  • Four layers, one call: Instead of making the client query each layer separately, the hybrid search does it in one call. This reduces latency and ensures consistent results.
  • SQL-level filtering: Temporal and status filters are applied in SQL, not in application code. This is faster and more reliable.
  • Graceful degradation: If FTS5 fails, keyword fallback kicks in. If graph has no matches, the other layers still return results. The system never fails completely.
  • Abstention over hallucination: Returning no results is better than returning wrong results. The LLM is told to abstain when the system has no relevant information.

Performance: Hybrid search completes in <1ms for typical queries (p50: 0.35ms). The four layers are queried sequentially but each is a fast indexed SQL query. The total latency is dominated by the slowest layer, not the sum.
