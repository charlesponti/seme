Knowledge Graph: Entity Resolution & Graph Traversal

How Seme builds and queries a knowledge graph from unstructured conversation text

1. The Problem

Traditional memory systems store facts as flat key-value pairs or text snippets. When a user says "I work at Ponti Studios in Edinburgh," the system might store two separate facts: "works at Ponti Studios" and "lives in Edinburgh." But it loses the relationship between these facts — Ponti Studios is in Edinburgh, the user works there, and the user lives there too.

A knowledge graph captures these relationships as a directed graph: nodes (entities) and edges (relationships). This enables traversal queries like "What's connected to Edinburgh?" or "How is Charles related to Ponti Studios?" that flat memory stores cannot answer.

2. Entity Resolution

Entity resolution is the process of determining whether two mentions refer to the same real-world entity. When the user says "Ponti Studios" in one turn and "Ponti" in another, the system must decide: are these the same entity?

2.1 Resolution Algorithm

Seme uses a multi-stage resolution pipeline:

  1. Name matching: Exact match (case-insensitive) against canonical names and aliases. "Ponti Studios" matches "Ponti Studios".
  2. Alias matching: Check if the mention is in the entity's alias list. "Ponti" matches an entity with alias "Ponti".
  3. Fuzzy matching: Levenshtein distance for near-misses. "Ponti Studois" (typo) matches "Ponti Studios" with distance 1.
  4. Type disambiguation: If two entities have the same name but different types (e.g., "Apple" the company vs. "apple" the fruit), use context to disambiguate.

2.2 Canonicalization

When a new entity is resolved to an existing one, the canonical name is preserved and the new mention is added as an alias. This ensures the graph doesn't accumulate duplicate nodes for the same entity.

Key insight: Entity resolution is the hardest part of knowledge graph construction. A false merge (combining two different entities) is worse than a false split (keeping them separate), because it corrupts the graph structure. Seme errs on the side of splitting.

3. Graph Traversal

Once entities and relationships are stored, the system needs to traverse the graph to answer queries. Seme implements two traversal algorithms:

3.1 N-Hop Neighborhood

Given a starting entity, find all entities and relationships within N hops. This uses a recursive CTE (Common Table Expression) in SQLite:

WITH RECURSIVE traversal(entity_id, depth, path) AS (
  SELECT id, 0, id FROM entities WHERE id = ?
  UNION ALL
  SELECT r.target_id, t.depth + 1, t.path || ',' || r.target_id
  FROM traversal t
  JOIN relationships r ON r.source_id = t.entity_id
  WHERE t.depth < ? AND t.path NOT LIKE '%' || r.target_id || '%'
)
SELECT DISTINCT entity_id, depth FROM traversal

The `path NOT LIKE` clause prevents cycles — the traversal won't revisit an entity it's already seen. This is critical for graph queries on cyclic graphs.

3.2 Shortest Path (BFS)

Finding the shortest path between two entities uses BFS (Breadth-First Search) implemented as a recursive CTE. BFS guarantees the shortest path in an unweighted graph:

WITH RECURSIVE path_search(entity_id, depth, path, rel_path) AS (
  SELECT id, 0, id, '' FROM entities WHERE id = ?
  UNION ALL
  SELECT r.target_id, ps.depth + 1, ps.path || ',' || r.target_id, ps.rel_path || ',' || r.id
  FROM path_search ps
  JOIN relationships r ON r.source_id = ps.entity_id
  WHERE ps.depth < 10 AND ps.path NOT LIKE '%' || r.target_id || '%'
)
SELECT path, rel_path FROM path_search WHERE entity_id = ? ORDER BY depth LIMIT 1

The `depth < 10` limit prevents infinite loops. The `ORDER BY depth LIMIT 1` ensures we get the shortest path.

4. Graph-Augmented Retrieval

The graph isn't just for display — it's used during retrieval. When a user asks "Where does Charles work?", the system:

  1. Matches "Charles" to an entity in the graph
  2. Traverses 2 hops from Charles to find related entities (Ponti Studios, Edinburgh, TypeScript)
  3. Includes these related entities in the retrieval context
  4. The LLM uses this graph context to provide a richer answer

This is "graph-augmented retrieval" — combining keyword/vector search with graph traversal to provide more context than flat memory search alone.

5. Storage Model

The graph is stored in SQLite with four tables:

  • entities: Nodes with name, type, aliases, description, confidence, source provenance
  • relationships: Directed edges with relation_type, description, weight, source turn/episode
  • entity_memory_links: Links entities to memories (subject, object, context, mentioned)
  • entity_turn_links: Links entities to turns where they were mentioned

Every entity and relationship has source provenance (source_turn_id, source_episode_id), enabling "why does the system know this?" queries and deletion cascades.

6. Performance Characteristics

  • Entity lookup by name: O(1) via index on name column
  • N-hop traversal: O(V + E) where V = vertices, E = edges within N hops. Recursive CTE is efficient for small N (≤3).
  • Shortest path: O(V + E) BFS. Limited to depth 10 to prevent runaway queries.
  • Graph snapshot: O(V + E) — returns entire graph. Used for visualization and export.

7. Design Decisions

  • SQLite over graph databases: SQLite is already the storage layer. Recursive CTEs provide graph traversal without adding a new database. Simpler deployment, single file.
  • Free-form entity types: No hardcoded type dictionary. The LLM determines the type. This allows the graph to adapt to any domain.
  • Directed relationships: Relationships are directed (source → target). "Charles works_at Ponti Studios" is different from "Ponti Studios employs Charles" even though they describe the same fact.
  • Provenance on everything: Every entity and relationship links to a source turn and episode. This enables audit trails and cascade deletion.

Trade-off: SQLite recursive CTEs are less efficient than dedicated graph databases (Neo4j, etc.) for deep traversal on large graphs. But for a personal memory system with hundreds to thousands of entities, SQLite is more than sufficient and dramatically simpler to deploy.
