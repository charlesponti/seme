Entity Extraction: LLM-Based NER & Chunking

How Seme extracts named entities and relationships from conversation text using LLMs

1. From Text to Knowledge Graph

Entity extraction is the bridge between unstructured conversation text and the structured knowledge graph. Given "I have a dog named Cyndi," the system must identify that "Cyndi" is an entity of type "animal" and that the user "has" this entity.

Traditional NER (Named Entity Recognition) uses trained models to identify entity spans. Seme uses an LLM instead, which provides richer extraction: not just entity identification but also type classification, alias tracking, and relationship extraction.

2. The Extraction Pipeline

Entity extraction runs as part of the extraction pipeline, after memory extraction. The pipeline:

  1. Builds a prompt from all turns in the episode
  2. Sends the prompt to the LLM with a system prompt defining the schema
  3. Parses the JSON response
  4. Validates each candidate against the schema
  5. Resolves entities (merge or create)
  6. Resolves relationships (link entities)

3. Chunking for Scale

A single LLM call can only produce a limited amount of structured output. For conversations with 10+ turns, the entity list becomes too large, causing JSON truncation or invalid output.

Seme chunks the turns into groups of 6 and makes parallel LLM calls:

const CHUNK_SIZE = 6;
const chunks = [];
for (let i = 0; i < turns.length; i += CHUNK_SIZE) {
  chunks.push(turns.slice(i, i + CHUNK_SIZE));
}
const results = await Promise.all(chunks.map(chunk => extract(chunk)));
// Deduplicate entities by name
const seen = new Set();
const unique = results.flatMap(r => r.entities).filter(e => {
  if (seen.has(e.name.toLowerCase())) return false;
  seen.add(e.name.toLowerCase());
  return true;
});

Parallel chunking reduces extraction time from O(n) to O(n/6) — a 6x speedup for large conversations. The deduplication step ensures the same entity mentioned in multiple chunks is only created once.

4. Open-Ended Entity Types

Early versions used a hardcoded list of valid entity types (person, place, organization, etc.). This caused failures when the LLM returned types not in the list (e.g., "animal" for a pet name).

The current approach accepts any type string from the LLM, normalizes it (lowercase, trim), and stores it. No validation dictionary. New types emerge naturally from the LLM's understanding of the context.

Key insight: The LLM is better at type classification than a hardcoded dictionary. By letting the LLM decide the type, the system adapts to any domain without code changes. "Tesla Model 3" becomes "other" or "vehicle" depending on context, and the system handles it gracefully.

5. Entity Resolution

When the LLM extracts "Cyndi" as an entity, the entity resolver checks if an entity with that name already exists:

  1. Exact match: Does an entity named "Cyndi" exist? If yes, reuse it.
  2. Alias match: Is "Cyndi" in any entity's alias list? If yes, reuse that entity.
  3. Create new: If no match, create a new entity with the LLM-provided type and description.

This ensures the graph doesn't accumulate duplicate nodes for the same entity mentioned across multiple conversations.

6. Relationship Extraction

Relationships are extracted alongside entities. The LLM identifies pairs of entities and their relationship type (works_at, lives_in, uses, etc.). Each relationship is validated:

  • Both source and target entities must exist in the entity list
  • The relationship type must be from the known set (or "related_to" as fallback)
  • Source turn and episode IDs must be valid

Invalid relationships (referencing non-existent entities) are silently dropped. This prevents graph corruption from hallucinated relationships.

7. Markdown Fence Stripping

LLMs sometimes wrap JSON responses in markdown code fences (```json ... ```). Both the memory and entity extractors now strip these fences before parsing:

let jsonStr = content.trim();
if (jsonStr.startsWith('```')) {
  jsonStr = jsonStr.replace(/^```(?:json)?\n?/, '').replace(/\n?```$/, '').trim();
}
const parsed = JSON.parse(jsonStr);

This prevents "invalid_output" errors from otherwise valid JSON responses.

8. Performance Characteristics

  • Single turn (1-6 sentences): ~5-10s (one LLM call)
  • Medium conversation (7-12 turns): ~10-15s (2 parallel LLM calls)
  • Long conversation (50+ turns): ~15-20s (9 parallel LLM calls, limited by API rate limits)

The parallel chunking makes entity extraction scale linearly with conversation length, but the actual wall-clock time is bounded by the slowest chunk (since they run in parallel).

Trade-off: Chunking loses cross-chunk context. An entity mentioned in chunk 1 and referenced in chunk 3 might not be linked. This is acceptable for entity extraction (each chunk is self-contained) but could miss relationships that span chunk boundaries. A future improvement could add a "merge pass" that links entities across chunks.
