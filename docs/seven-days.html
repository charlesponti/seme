Seven days of making Seme less wrong

Seme engineering log · week of 3–9 November 2026

This week was mostly about one question: when Seme says it remembered something about a person, is it actually right, and how would we know? That turned into tougher evals, a skill router, a relation judge that doesn't rely on exact words, a pile of storage and tooling cleanup, and a faster extraction pipeline.

01Evals that can actually fail

The old eval suite was too easy. A handful of short, tidy diary entries made nearly everything look fine, so it couldn't show whether the skills system was doing anything. The fix was to write a harder one.

The new people-and-relationships suite models a five-year diary. A generator builds a timeline across food, friends, places, money, trips, career, family, emotions, and goals, then writes the entries a person might plausibly submit day to day. Every entry has gold labels for entities, relations, and the memories that should come out of it. Third parties show up in passing all the time, because that's how real diaries read.

The grader works in layers. A string grader handles exact entity matches. A relation judge handles the cases where the same fact can be said a dozen ways. Results report precision, recall, and F1, plus pass-rate and pass^k so repeat-run flakiness is visible. Latency is tracked too, since a memory system that takes a minute per entry isn't much use.

02Skill modules and the router

Seme now has three domain skill modules: food-and-health, people-and-relationships, and work-and-projects. Each one is a SKILL.md with guidance for the extractor. For each chunk of text, a router embeds the chunk and picks the modules whose descriptions are closest, using the local Ollama embedding model (qwen3-embedding). Module embeddings are cached in SQLite in a skill_embeddings table, so they're only recomputed when a description or the model changes.

The router fails open. If embeddings aren't available, the chunk just gets extracted without skill guidance rather than failing. Along the way we removed the SEME_SKILLS=off switch. Skills are the direction, and keeping a parallel off-path around was just more code to test.

When we first ran the tougher eval with skills on, the scores were worse than they should have been. That led to the bug in the next section.

03The third-party facts bug

Skills-on was dropping relations. The cause was a prompt contradiction. The skill guidance said to extract a third party's facts as relations from that person, but the base extraction rules, rule 9 in particular, said to tag reported or quoted statements with a modality and not treat them as confirmed. Put together, the model was often treating "Dev says X is hiring" as hypothetical and dropping it.

The fix was to rewrite both places so they agree. Rule 9 now reads:

9. Tag hypothetical, joking, negated or quoted statements with that modality. A claim by a
   third party that the user reports ("Dev says X is hiring") is stated: extract it from that
   person. Use quoted only when the user repeats someone's exact words in quotation marks.

The skill bullet got the same treatment: third parties mentioned in passing still get entities, and a reported claim becomes a relation from that person. After that, skills-on relation recall came out above the skills-off baseline, 0.836 against 0.801.

04Grading relations without word matching

This was the most useful argument of the week. The first relation grader leaned on surface wording: strip determiners, match the words. That breaks immediately for people who don't write in English, and it's also just the wrong tool. "A burger and fries go together" is obvious to any language model without a single matching word.

Rule of thumb we landed on: don't rebuild language understanding from scratch. Decades of computational linguistics and a lot of working libraries already exist, and most of them run on Node too.

So the relation judge now uses a natural language inference model, MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7 (quantized, run locally through transformers.js). Each relation gets turned into a short sentence, something like "Dev is hiring", and the judge asks whether the source text entails it. The entailment score is compared to a threshold.

The threshold came from data, not a guess. We hand-audited a stratified sample of 100 judged relations. At the first threshold we tried, 0.25, recall was about 0.77. At 0.10 the audit estimates precision around 0.99 and recall around 0.98, so SUPPORT_THRESHOLD is now 0.10. These are audit estimates from one sample, so treat them as a good starting point, not a guarantee.

05Eval results live in SQLite now

Eval runs and baselines were JSON files committed into the repo. That bloats git history fast, and every new baseline is a diff nobody wants to read. Everything now goes into ~/.hominem/seme.evals.db (override with SEME_EVALS_DB), with two tables: runs and baselines.

A one-time importer moved the old JSON results over, and we only deleted the JSON copies after checking that every run and baseline was in the database. Output folders are gitignored now. The runner reads baselines from the database, so --baseline still works the same way.

06BBC corpus and loader

We load a BBC article corpus through the API as a stress test for ingestion. The corpus builder and loader both got rewritten for speed and resilience:

  • Corpus builder (scripts/bbc-corpus.mjs): bounded concurrency, retries, ordered streaming output, and resume, so a crash doesn't mean starting over.
  • Loader (scripts/bbc-load.mjs): streams input instead of loading it whole, retries POSTs only on 429 and 503, and drains by polling each episode's status rather than sleeping.
  • Duplicate extraction gone: the old loader also called the session-end endpoint, which re-ran extraction on every episode. It's removed.

On a 10-article run, wall time went from 66 seconds to 14. The first run through the 300-article corpus hit provider rate limits when hundreds of episodes extracted at once, so scripts/seme-retry-extraction.mjs retries document episodes that came back with no memories or no entity links, one at a time, reusing the stored turns. It defaults to three workers with a short delay between jobs.

07Provenance and ingest progress

Every entity and relation now records where it came from: the turn, the source, and the evidence quote. Provenance routes expose that for the UI. There's also a GET /ingest/episodes/:id/status endpoint that reports the current extraction stage and counts while an episode runs. Progress is held in memory, so a restart forgets it and returns a 404, which is fine for a status that only matters while work is in flight.

The web app picked up an entities browser, search on the dashboard, and an add-memory sheet to go with it.

08The move to pnpm

The repo is now a pnpm workspace (apps/*) pinned to pnpm@11.23.0. A few things we ran into along the way, so future us doesn't have to:

  • allowBuilds in pnpm-workspace.yaml is what lets better-sqlite3 and onnxruntime-node run their install scripts. protobufjs is explicitly off.
  • Docker images build from the repo root with pnpm --filter seme --prod deploy --legacy. The --legacy flag is required because pnpm 10+ refuses non-injected workspace deploys otherwise.
  • The root .dockerignore patterns need **/ prefixes. Without them, apps/api/.env and nested .db files slip into the build context. We planted a fake .env and leak.db to check, and both are now excluded.
  • After a prod deploy, pnpm wanted to purge node_modules. CI=true pnpm install --frozen-lockfile fixed it.

09Making extraction faster

Extraction used to run in sequence: memory first, then entities and relations. Entity extraction only reads the turns, though, so it doesn't need to wait on the memory call. The pipeline now starts entity extraction first and awaits it where its result is consumed. The wrapper never rejects, so an early return from the memory step can't leave a crashing promise behind.

10What's still open

  • The memory LLM call is now the critical path. Shortening it means changing the prompt or the model, and either one can move quality, so that needs a deliberate eval run rather than a quick tweak.
  • Post-LLM writes are still sequential. Resolving and saving entities and relations after extraction is the next thing to parallelize, worth roughly a second or two per episode.
  • Prompt audit leftovers. The agent_inferred source type conflicts with "only extract what the text says". The evidence quote limit (300 characters) doesn't match the verified quote limit (400). The food skill has an undefined "allergy relation" wording. Memory recall has been flat around 0.70 for a while.
  • Lint and format debt. About 25 lint errors and a pile of format issues predate this week, and we left them alone on purpose so the week's changes stayed reviewable.
  • The pre-commit hook fails on lockfiles. The lint-staged glob catches pnpm-lock.yaml, and oxfmt doesn't handle YAML, so lockfile commits need --no-verify for now. The glob should exclude YAML.
  • Fly deploy isn't verified. The local fly.toml build context needs to point at the repo root now that Docker builds from there.

The through-line for the week: fewer things we have to trust on faith. Evals that can fail, a judge with a measured threshold, a baseline that lives in a database instead of a diff, and a pipeline that's quicker to find out when it's wrong.
